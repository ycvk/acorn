# ADR 0009 后台把关切推进到成品

owner 交代一件要花几天的事，比如把一个在追的项目近几个版本的变化整理成一份文档，agent 会为它建一个关切。之后 agent 在后台能为它做的只有游思：每个游思时段按 id 取第一个到期的关切，在夜思与所有游思共用的 Thoughts 线程里跑一次，输入要求留下一个念头、一点进展或下一次约定。游思技能要求的工具是 `think`、`recall`、`memory_read`、`concern` 与 `knowledge_search`，结果留在线程和记忆里，工作机用不上。owner 在此刻页看到的是关切的标题和一行理由。

具体有几处缺口。关切只有标题、理由与复查时间，没写做完要交给 owner 什么，agent 没有收口的目标，owner 也无从判断做到了没有。推进同一件事的几次运行散在 Thoughts 线程里，夹着别的关切和夜思，被总结压缩后接不上，做出来的文件也落在 owner 不看的线程里。按 id 排在前面、又没设复查时间的关切每个时段都会被选中，排在后面的关切轮不到。约定可以经 `concern_id` 关联关切，醒来时的输入却只有约定内容，agent 要从“当下”列出的全部关切里自己认出是哪一件。

同类产品的做法是交给它一个目标，它在自己的电脑上持续推进，交回可以审阅的成品。Acorn 已经有关切、约定、工作机、审批与每日预算，缺的是把它们接成一条从交代到交付的路径。

## 决策

### 关切的成品

关切增加 `outcome`：做完时交给 owner 的东西，写明形式和判断做完的标准，例如“一份 Markdown，列出 v1.4 到 v1.7 的不兼容变更和升级步骤”。owner 交代需要做出东西的事时，agent 建立关切并写下 outcome；只需跟进状态的事（等快递、等回复）不写。outcome 和标题一样随每个 revision 保存，owner 改主意时 agent 基于读到的 revision 修改。

有 outcome 的关切只由 owner 的确认解决。交付之后关切转为 `waiting`，理由写明交付了什么、在哪里；owner 在对话里确认后，agent 以这条 owner 消息为来源解决它。没有 outcome 的关切沿用现有规则，owner 的确认或成功的工具结果都可以作为解决依据。

### 在交代它的对话里推进

关切记下建立它的对话。推进它的游思在这个对话里运行，与约定醒来进入立约定的线程一致：运行带着这个对话的历史与摘要，回复和 `send_file` 发出的文件都留在 owner 交代这件事的地方。夜思里建立的关切属于 Thoughts 线程。

删除对话是遗忘请求，在这个对话里建立的关切随之排除，不再列出，也不再推进。

### 游思做事

游思输入列出关切的 outcome、最新理由与复查时间。游思技能改为：先在本对话里回看上次做到哪里，再做下一步具体的事。需要动手时用工作机，工作文件放在 `~/work/<concern-id>/`；`/home/agent` 是持久卷，跨运行与镜像重建保留。需要外部资料时用 web 工具与浏览器。每次结束用 `concern` 记下这次做了什么、还差什么和下次复查时间。达到 outcome 时，用 `send_file` 或 `knowledge_write` 交付，调用一次 `notify_owner`，把关切转为 `waiting`。

没有 outcome 的关切，游思照旧检查进展与等待条件。

### 选哪件、多久推进一次

每个游思时段从到期的 `active` 与 `waiting` 关切里选最久没有修订的一件。关切所在对话的最新 run 还在运行或等待审批时，跳过这件关切。

agent 想在下一个游思时段之前接着做，用带 `concern_id` 的 `schedule_wake` 约一次醒来。约定醒来的输入在约定内容之后附上关联关切的 outcome 与最新理由。游思与约定醒来都计入 `wake.daily_limit` 与 `wake.daily_tokens`，预算耗尽时推进留到下一本地日。

### 审批

后台推进使用的工具与 owner 在场时相同，照常经过 owner 的规则与 Jev 审查。需要审批的调用让 run 停在 interrupted 并推送，owner 在手机上批准后由服务端续跑。工作机之外有后果的动作仍等 owner 批准。

### App

此刻页“正在跟进”的每一项显示 outcome 与最新理由，点开进入关切所在的对话。`NowConcern` 增加 `outcome` 与 `thread_id`。

### 边界变化

本决定扩展 ADR 0004 中游思“产出一个念头、具体进展或合适的下一次约定”：对有 outcome 的关切，游思在工作机上推进并交付成品。关切的解决规则对有 outcome 的关切收紧为只认 owner 的确认。

## 分期

| 期 | 内容 | 验收 |
|---|---|---|
| S1 | 关切记下所在对话，游思在该对话里运行；按最久没有修订选关切，跳过对话忙碌的关切；约定醒来的输入附上关联关切；删除对话排除其中建立的关切 | 交代两件持续跟进的事并配两个游思时段，两件都轮到；同一件事的第二次推进在原对话里接着第一次的进展；删除其中一个对话后，那件关切从此刻页消失且不再被推进 |
| S2 | 关切的 `outcome`；游思技能改为在工作机上做事并交付；有 outcome 的关切只由 owner 解决 | 在真实主机上交代一件一两天能做完、需要动手的事，比如把一个在追的 GitHub 项目近几个版本的变化整理成一份 Markdown：每次推进留下关切 revision，`~/work/<id>/` 里的文件随之增长，中途需要审批的操作停下推送、批准后接着做；成品发在原对话里，只推送一次，关切停在 waiting，owner 确认后变为 resolved |
| S3 | 此刻页显示 outcome 与最新理由，点开进入关切所在的对话 | owner 在此刻页看到这件事做到哪一步，点进去就是交代它的对话，成品在里面 |

## 代价

- 后台推进会持续消耗 token。starter config 的 `wake.daily_tokens` 为 0，即不限；让 agent 长期在后台做事之前，owner 需要设一个上限。
- 游思运行在 owner 的对话里，owner 回到对话时会看到 agent 在自己离开期间留下的推进记录，这些记录也进入这个对话之后的历史与摘要。
- 成品质量取决于模型能否独立把一件事做完；方向做偏要等 owner 看到成品或中途的推进记录才能纠正。
- 工作文件随关切累积在工作机的 `~/work/` 下，对之后的所有 run 和技能脚本可见。
- 每个游思时段只推进一件关切；关切多时每件轮到的间隔变长，需要更多游思时段或约定醒来，两者都受每日预算约束。
- 有 outcome 的关切等 owner 确认才结束；owner 不回应时它停在 waiting，只在复查时间到了被游思看一眼。
